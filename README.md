## What It Does

PathPilot finds the optimal walking route between any two buildings on UC Berkeley's campus — not just the shortest path, but the **least congested** path, predicted 30 minutes into the future using a trained Random Forest classifier.

Users pick a source and destination, and PathPilot returns two routes side-by-side:
- **Fastest** — raw Dijkstra shortest path
- **Smart** — congestion-aware reroute that avoids predicted crowds

A live D3.js heatmap overlays every building with a color-coded congestion level (green → yellow → red) that updates as you drag a 24-hour time slider.

## Technical Highlights

### Graph Layer
- Modeled UC Berkeley as a **weighted directed graph** with 56 buildings and 1,786 edges
- Edge weights computed from real Haversine walking distances
- 122 hand-curated edges encoding real campus footpaths; remaining edges auto-generated by proximity threshold
- Dijkstra's shortest path with a **congestion penalty hook** — predicted high-traffic buildings receive +320m edge weight penalties, forcing reroutes through quieter paths
- Achieves **sub-100ms API response times** by loading the graph into memory at startup

### ML Layer
- Trained a **Random Forest classifier** (300 trees, scikit-learn) on 5,000 synthetic foot-traffic records
- 22 features per observation: cyclic hour encoding (sin/cos), day-of-week, minutes until/since class, building type one-hot (lecture/lab/library/cafe/gym/landmark), and campus area one-hot
- Class schedule features (`mins_to_class`, `mins_since_class`, `class_soon`) capture the transitional medium-congestion state during building fill/drain cycles
- **Margin filtering** removed 1,537 ambiguous boundary samples near label thresholds, improving test accuracy from 73% → **84%**
- 9.4% overfit gap (train 93% / test 84%) — healthy generalization
- Heatmap inference batched into a **single vectorized `clf.predict()` call** across all 952 building×hour pairs, reducing computation from 74s → 0.07s per day

### API Layer
- **FastAPI** REST backend with 6 endpoints: `/route`, `/route/compare`, `/buildings`, `/buildings/{id}`, `/heatmap`, `/heatmap/full`, `/heatmap/stats`
- All 7 days of heatmap data pre-computed at startup and cached in memory — `/heatmap/full` responds instantly
- **PostgreSQL** route query logging via SQLAlchemy — tracks every route request for analytics
- 143 pytest tests across 3 phases, all passing

### Frontend
- **React + Leaflet** map centered on UC Berkeley with CartoDB dark tiles
- **D3.js color scale** maps congestion level (0–2) to green → yellow → red circle markers on all 56 buildings
- Side-by-side route comparison: blue dashed (fastest) vs green solid (smart) polylines drawn on the map
- **24-hour time slider** with play/pause animation — reads from a pre-cached heatmap so scrubbing is instant with zero API calls
- Day-of-week selector that reloads the heatmap for any weekday/weekend pattern

### Deployment
- **Docker Compose** orchestrating three services: FastAPI API, PostgreSQL, and Nginx
- **Nginx** reverse proxy serves the Vite-built React bundle and proxies `/api/*` to FastAPI
- Deployed on **AWS EC2** (t3.small, Ubuntu 22.04)
- **GitHub Actions CI/CD pipeline** — on every push to `main`: runs all 143 tests, builds the React frontend, SCPs the dist bundle to EC2, and restarts the API container via SSH

## Key Engineering Decisions

**Why Random Forest over a neural network?**
Random Forest is interpretable — feature importances confirm that building type and time of day dominate predictions, which matches real campus behavior. It also requires no GPU, making EC2 deployment straightforward, and achieves 84% accuracy on a 3-class problem with only 3,463 clean training samples after margin filtering.

**Why synthetic data?**
UC Berkeley doesn't expose real-time occupancy sensors publicly. The synthetic generator encodes real campus patterns — class schedules, dining peaks, library evening surges — with Gaussian noise to simulate sensor variance. The resulting model produces predictions that match observable campus behavior.

**Why batch vectorized inference?**
Initial heatmap computation called `predict_proba` per building per hour slot in a loop — 1,848 sequential model calls taking 74 seconds. Stacking all feature vectors into a single NumPy array and calling `clf.predict()` once reduced this to 70ms, a **1,057× speedup**, enabling the pre-computed startup cache.

**Why pre-cache all 7 days at startup?**
The frontend time slider and day-of-week selector would otherwise trigger expensive recomputation on every user interaction. Pre-caching all 7 days takes 0.4 seconds at startup and makes every subsequent `/heatmap/full` request O(1) dictionary lookups.
